# Grocy 联动与独立订单收货

## 入口与正常流程

「设置」集中提供布局／模板、备份及 Grocy 配置；「库存管理」按父子产品树浏览库存、批次与告警，默认隐藏无库存且未设置最低库存、也无到期告警的产品，可勾选「显示全部产品」。筛选保留父产品上下文，父产品优先显示 Grocy 返回的累计库存与累计开封数量。产品编辑提供分类、父产品、无自有库存及累计最低库存设置；选中或保存产品后，可在同一编辑区维护该产品的单位换算，使用单位名称展示。位置、单位、分类及采购地点可单独管理。「订单与收货」管理待收、部分收货、已收、历史认领及结算／退款。

普通「记一笔」及「补记工作台」均可添加商品并关联 Grocy；添加商品后按可独立收货的已付款订单保存，不添加商品仍是普通消费。购买商品可以全部、部分或完全不关联 Grocy。采购数量独立于费用分录。单商品自动使用整单金额，多商品只需把包含优惠与运费的订单金额分配到各行，合计必须等于订单金额。系统按“分配金额 ÷（采购数量 × 库存换算倍数）”自动计算库存单价，后端使用十进制复算到 8 位小数。例如 120 元购买 2 箱、每箱 12 瓶，自动得到每瓶 5 元。2026-10-20 按用户要求：价格使用账本币种，忽略 Grocy 的货币配置与显示符号，不进行汇率转换，也不因其货币配置变化阻断提交。库存数量的单位换算仍必须有效；缺少直接换算时不能猜测。无自有库存父产品和停用产品不能作为采购入库关联，需选择可入库的子产品。Grocy 创建采购／库存单位不同的产品时会自动生成换算记录，应在产品编辑内选择该记录修改倍数。

购买预览不产生在途数量；购买正式保存后也不增加库存。到货后选择实际日期、商品和本次数量，未收到的行填 0，核对位置、保质期和库存单价后确认。每次实收单独保存，不能超量；未关联商品仅记录收货。已付款订单不新增账务，也不生成 0 元占位；先用后付可只收货、单独结算，或同时收货并结算。实收、付款结算和库存同步分别展示结果，一个失败不伪装成全部失败或全部成功。

预览后账本变化可能使原结算无法再提交。先恢复原请求核对；若实收已保存，可使用「保留收货并结束原结算请求」，后端确认未写入才取消原结算，继续下一批收货或在结算与退款页重新预览。独立账务同样提供「核对并结束原账务请求」。已经写入的账务保持完成，不会因结束请求被删除。

缺货告警始终依据 Grocy 实际库存。在途和实收但未确认入库的数量另列；库存 1、最低 6、待收 12 时仍显示缺货。告警的购买按钮只预填，不自动下单、记账或入库；建议采购数量按缺口扣除待收与已收未同步后，使用已知的直接换算计算。没有净缺口或换算未知时数量留空，由用户核对填写。到期提示本身不代表必须补货。

库存页可开封、跨位置转移、消耗和手动入库。使用库存单位；开封必须选择批次。手动入库需确认与订单收货无关，避免同一采购重复入库。开封／消耗／转移接口使用 Grocy 服务器当前时间，不支持回填历史日期。无自有库存产品仅汇总展示与编辑，库存操作在子产品上进行。首版不支持皮重、菜谱和家务等其他模块。

消耗和转移的来源位置只显示该产品有库存的位置；开封只显示有未开封库存的位置和批次。默认位置无可操作库存时自动选择可用位置，无可操作库存时不能预览；手动入库及转移目标仍可选择全部位置。产品在 Grocy 中启用“开封后自动转移”并配置不同的默认消耗位置后，本页面开封也会触发该规则，仅转移本次开封数量，预览会显示目标位置。确认前若该规则变化，需重新预览；开封及关联转移日志按同一事务核对，响应丢失时仍先核对而不自动重发。

## 连接与权限

在「设置 → Grocy」填写实例根地址、API Key 和默认值。地址可以包含反向代理子路径，不加 `/api`，不在 URL 中填写 Key。请求由账本后端发出：同 Docker 网络可使用 `http://grocy:80` 等服务地址；两台设备使用后端实际可达的受保护地址。浏览器可访问并不证明容器可访问，容器内 `localhost` 也不代表 NAS 主机。

Key 只写入后端 `state/grocy.json`，接口不返回 Key，浏览器不持久保存。状态目录和备份均应限制访问。连接测试逐接口显示读取成功、权限不足或连接错误，同时显示实际版本，不修改库存，也不能证明全部写权限；产品、库存操作及日志读取权限需要按实际操作验证。HTTP 错误、重定向、超时不会自动被当作可重试写入。

适配范围为 Grocy 4.x；本次隔离实测 **4.7.1**（PHP 8.5.11、SQLite 3.53.4）。这不保证所有未来 4.x 版本兼容。`latest` 是镜像标签，不是版本号；更新前保留版本／镜像摘要与完整备份，更新后重新测试连接，在测试产品上核对必要动作及日志字段。不要把首次兼容验证放在真实收货上。

有关联或正式发送库存操作后，不能直接更换实例地址；相同产品数字 ID 在另一实例中没有相同含义。设置页可查看已关联订单商品、库存操作及待处理状态。仅生成手动库存预览不会建立永久绑定；更换实例后旧预览不能发往新实例。迁移域名、容器服务名或 Grocy 数据库前，应停写并核对实例、日志和状态备份，不能通过删除绑定文件强行切换。本版不提供把已有历史自动重新绑定到另一数据库的入口。

## 异常与更正

每次商品入库保存固定操作编号、目标实例、数量、价格、位置和日期；编号同时写入 Grocy 备注。超时后保留原请求，通过完整入库事务、当前批次与后续开封／消耗／转移核对。部分开封产生的新批次使用继承备注追踪。总库存相等不能证明该操作成功；暂时查不到日志也不能证明没执行。

后台会核对未知结果并退避重查，不自动重发可能已执行的写入。明确未发送才可自动重试。手动开封／转移／消耗缺少可可靠查询的原响应事务编号时，需要人工核对，不能凭库存差值重发。人工重发需说明证据，确认原执行停止且没有副作用；人工核实成功／停止只记录结论，不修改 Grocy。保留原操作编号，不删除未知操作后新建同一入库。

取消待收只取消尚未到货的数量，不退款，不删除实收历史。仅退款、差价返还使用结算与退款页，不扣库存。真实退货先核对原批次，在库存页对实际退回的批次执行消耗，再记录退货说明；退款另行处理。误录实收可申请作废，系统先核对入库及后续操作；已经消耗、转移或无法确认结果时阻止自动撤销。撤销响应丢失只核对，不重复撤销。已收货订单不能直接改商品快照或删除原记录；商品没有有效收货（包括相关收货全部已作废）时可显式更正产品、数量与价格，保存原商品快照作为审计。订单全部收货已作废时可解除管理，再单独更正账务；已作废实收、库存操作与解除时的快照仍保留，不随解除删除。

## 备份、重建与恢复

必须分别保存三类数据：

| 数据 | 内容与恢复作用 |
| --- | --- |
| Beancount 账本目录 | 购买、付款、退款和固定订单标识；账本 Git 备份只包含这一部分 |
| 完整应用 state 目录 | `writes.sqlite3` 中的订单商品、实收、预览、同步操作、审计及请求去重；`grocy.json` 的凭据与实例标识、`grocy-bindings.locked` 的实例保护；其他配置和访问／备份凭据 |
| Grocy 自身持久数据 | 库存、产品、批次、日志、用户和 API Key；按 Grocy 的部署方式备份其完整数据卷 |

备份前停止写入并停止应用进程，确认 Grocy 侧在途请求已经结束；不要运行两个共用状态目录的应用写入实例。再复制完整 state、账本及 Grocy 数据卷并标明时间和版本。运行中的 SQLite 文件不能仅靠直接复制主文件备份；需要停止服务或使用一致性 SQLite backup，并保留其它配置的一致快照。备份中含凭据，不上传到公共仓库。

重建应用容器保留原账本、state 挂载路径和 Grocy 数据卷。恢复前停止原应用与所有可能继续执行的 Grocy 请求，保存当前数据副本，再恢复一致的三类备份。若必须恢复不同时间点，先停用联动，逐项比对订单编号、收货操作编号与远端日志，确认后再启用。恢复不能消除已在 Grocy 生效的写入。

启动时旧待发、发送中、失败和手动预览统一进入结果待确认；旧收货预览恢复提交时只创建待核对操作。发送新入库前也会查询已有同编号日志。没有找到日志的旧操作仍不会自动重发，需确认原执行已经停止并人工判断。若备份早于全部预览记录，或浏览器原请求也丢失，系统无法凭空重建业务意图；必须先人工对账再新建操作，不能把“未查到本地记录”当成安全重做依据。

升级前复制完整数据和镜像摘要；回滚程序时同时评估新字段与旧版本兼容，优先恢复相匹配的应用版本、账本和 state 快照，并核对 Grocy 后续日志。不要用清空 state 作为回滚方式。

## 验证与现场边界

`tests/test_grocy_live.py` 是显式启用的真实 API 验收，默认跳过。只允许一次性 loopback 测试实例；创建测试资料并修改库存，严禁连接家庭生产数据库。测试实例使用 CNY 和独立测试 Key（或仅回环接口关闭鉴权），在项目外的临时目录运行：

```powershell
$env:GROCY_TEST_URL = 'http://127.0.0.1:18993'
uv run pytest tests/test_grocy_live.py -q -s
Remove-Item Env:GROCY_TEST_URL
```

已实测资料新建／换算编辑、120 元 2 箱共 24 瓶、分批实收、结算、开封拆批、转移、消耗、远端成功响应丢失、恢复仅含预览的旧 state 后无重复入库。故障与兼容分支由单元／接口测试补充。真实 NAS 网络、部署凭据及容器重建尚需在可用环境核验；本机 PHP 服务和重建应用对象的结果不能替代 Docker／NAS 现场验收。
