# 产品规划说明

## 产品目标与规划依据

做一个适合个人每天使用的 Beancount 网页记账工具：下班后集中补记白天的消费，之后随时记一笔；沿用现有账本组织和记账语义，定时将已验证的变更提交并推送到 GitHub。

- 规划日期：2026-09-30。
- 账本：[silevilence/MyBill，master-1](https://github.com/silevilence/MyBill/tree/master-1)。分析固定在提交 [`6c09193`](https://github.com/silevilence/MyBill/tree/6c09193b0858a37055e9fb530a547f8ccc4f73c9)，提交日期为 2026-09-01，提交说明为 `2026.08 bak`。
- 重点观察 2026 年 6—8 月，按交易实际日期统计，同时读取专项分类文件；9 月尚未同步的本地记录不在分析范围。证据与详细模式见 [账本分析](ledger-analysis.md)。
- 本轮交付为需求规划，所有实现任务仍处于「计划中」。分析采用源码文本和 include 结构核对，不代表已通过 Beancount 完整校验。

### 已确定的约束

1. **Python 后端 + React 前端**。账本解析、金额语义与校验调用 Beancount 库；前端不自行实现复式记账校验。
2. **本地开发不依赖 Docker**。开发机没有 Docker，启动、调试、测试均直接运行 Python 和前端开发服务。Docker 镜像只在最后的 GitHub Actions 发布阶段构建和发布。
3. **Beancount 文件是账务事实来源**。应用缓存和草稿不得成为另一份不可还原的正式账本；应用代码仓库与 MyBill 账本工作副本分离。
4. **第一版固定兼容 MyBill 布局**，不迁移、不重新整理历史账本。文件选择规则集中在后端独立模块，前端按业务类型提交；未来可替换为配置规则。
5. **记账和 Git 同步分开**。保存成功表示已可靠写入本地账本；GitHub 暂时不可用不应阻止记账。自动同步包含 commit 和 push，不能把“有本地提交”显示为“已备份”。

### 规划默认值与范围

以下为待实际使用反馈调整的默认值，不冒充用户已确认的要求：

- 单用户、单账本、电脑键盘录入优先，经局域网或私有网络访问；保留窄屏可用性。公网开放、多用户权限体系、原生移动端不列入第一版。
- 界面使用中文，记账日期以 `Asia/Shanghai` 为准；跨午夜补记时固定当前选中的记账日。
- 建议技术组合为 FastAPI + React/TypeScript + Vite。具体 Python、Beancount 和 Node 版本在兼容性任务中锁定，不根据文本检查假定兼容。
- 定时同步默认每 5 分钟检查，距最近一次保存至少 60 秒再同步；均可调整或关闭，另提供「立即同步」。这是应用内功能，不是在当前聊天中创建定时任务。
- 支持连接既有本地账本工作副本，或在空目录克隆指定分支。连接本地副本优先满足尚未上传的 9 月记录；首次启用自动同步前，展示待纳入的既有变更并由用户在产品内选择是否纳入。
- 默认不自动填入推测的消费或收益金额，不因历史高频就自动生成正式交易。先给推荐模板，由人确认。
- 第一版不做银行/支付宝/微信账单导入、OCR、自动读取交易平台、预算分析仪表盘和通用账本布局编辑器。

### 第一版固定文件路由

入口为 `main.beancount`，经根 `index.bean` 包含历史导入及 `txs/index.bean`。具体依据见 [根入口](https://github.com/silevilence/MyBill/blob/6c09193b0858a37055e9fb530a547f8ccc4f73c9/main.beancount)、[根索引](https://github.com/silevilence/MyBill/blob/6c09193b0858a37055e9fb530a547f8ccc4f73c9/index.bean)和[分类索引](https://github.com/silevilence/MyBill/blob/6c09193b0858a37055e9fb530a547f8ccc4f73c9/txs/category/index.bean)。

| 新建记录的业务类型 | 文件位置 | 写入约束 |
| --- | --- | --- |
| 日常消费、淘宝下单/结算/退款、转账还款、水电费 | `txs/YYYY/MM.bean` | 按新交易的实际日期路由；缺月或跨年时补齐各级 include，避免重复 |
| 每日余额宝收益 | `txs/category/yuebao.bean` | 保留既有收益账户与省略金额的写法 |
| 工资、奖金 | `txs/category/salary.bean` | 在现有 `pushtag #salary` / `poptag #salary` 范围内正确写入 |
| 话费 | `txs/category/phone.bean` | 与水电费分开；允许选择不同号码备注和付款账户 |
| 余额核对断言 | `txs/category/balance.bean` | 区分 `balance` 与真实收支，不自动用 `pad` 抹平差异 |
| GnuCash 导入历史及现有账户定义 | `gnucash/gnucash.beancount`、`gnucash/import.beancount` | 第一版只读兼容；不作为新交易的写入目标 |

路由按明确选择的业务类型决定，不靠商户名称或模糊关键词猜测。编辑历史记录默认保留原文件位置，不能因历史交易日期与所在月份不一致就自动搬迁；后续显式迁移应独立设计。

### 日常模式对应的产品行为

下表是从历史模式导出的设计建议，频次与具体证据见 [账本分析](ledger-analysis.md)。2026 年 6—8 月共观察到 342 笔交易，其中 88VIP 购物 50 笔、超市消费 67 笔、确认收货结算 10 笔、余额宝收益 90 笔。统计按实际日期覆盖所有有效包含文件，不能直接按月文件中的行数计算。

| 观察到的模式 | 要解决的问题 | 第一版行为 |
| --- | --- | --- |
| 淘宝「88VIP每日红包」反复出现，付款账户并不固定 | 反复填写商户、摘要、分类很慢 | 快捷模板预填常用项，重点输入实际金额、商品备注和本次付款账户；不假定每天都有或金额固定 |
| 淘宝部分交易先挂待付款负债，确认收货时换成实际付款账户 | 下单与结算容易重复计为消费 | 分开提供「购物」与「确认收货/结算」；结算不新增支出 |
| 超市食材与餐饮频繁发生，商品可有不同分类和备注 | 每天有多笔相近但并不相同的支出 | 最近商户推荐、连续录入、同单多项分类及逐项备注 |
| 余额宝收益存在独立文件 | 每天重复操作，且容易漏填或重复 | 按日金额表格、缺口提示、已有记录回显；不估算收益 |
| 工资、话费有独立文件，水电费在月文件 | 使用同一种“定期支出”路由会写错文件 | 分业务模板，金额每次确认；工资允许年终奖等额外入账 |
| 近期有转账、信用账户还款和赔偿；较早历史有退款冲减费用 | 资产移动或返还容易算成新增消费 | 转账、还款和退款分别处理，可关联原交易；不把优惠券负项等同于退款 |
| 有多 posting、posting 级 `memo`、外币及预算权益辅助分录 | 简单的“金额+分类”表单会丢信息 | 基础表单外提供高级分录编辑和原文预览，已有复杂记录须无损保留 |
| 月文件中存在日期属于其他月份的记录 | 按文件名查“今天”会漏账 | 所有包含文件统一按交易日期检索，不自动修正历史摆放 |

## 任务组织与估算

任务按交付依赖排列，估算为单人专注开发时间，每项约 1—3 天，不含需求调整和等待外部服务时间。先交付可安全记一笔的闭环，再优化日常效率，最后完成同步与发布。

任务清单见 [ROADMAP](../ROADMAP.md)。
